Решение о внедрении

Использовать за несколькими независимыми границами защиты

Для локального пилота текущая лаборатория существенно ограничивает поверхность. Для корпоративного сервиса я рекомендую закрытый TLS ingress с MFA, приватные state services, ограниченный egress и отдельную среду исполнения кода. До выдачи доступа недоверенным пользователям нужны исправления и отрицательные тесты identity/sharing.

Главный риск: пользователь публичной ссылки может получить owner-wide MCP retrieval (F01), а отключённый пользователь — сохранить API/beta-доступ (F02). Сетевая изоляция уменьшает доступность путей; корректность полномочий и отзыва требует исправления кода.

Что сделать первым

  • Сохранить блокировку /api/v1/mcp и закрыть отдельный MCP-listener; не публиковать raw API/Admin.
  • Проверять offboarding со всеми credentials, отдельно отзывать API и beta.
  • Не применять Local code provider к недоверенному коду; ограничить модельные и tool destinations на сети.

На что не полагаться

  • api.host/admin.host и DISABLE_PASSWORD_LOGIN не обеспечивают обещанное ограничение.
  • Порт 443, HTTPS в URL и verify «по умолчанию» не доказывают валидируемый TLS.
  • SSO/audit YAML и enterprise labels не добавляют отсутствующую OSS реализацию.

Это статические выводы о проверенных путях кода, а не результат эксплуатации вашей работающей установки. Эксплойты, нагрузочные запросы, изменение конфигурации и обновление сервисов не выполнялись.

F01 · HighCWE 863 · уверенность: высокая по коду

Публичная ссылка даёт права владельца через MCP

Получатель ссылки на чат/агент берёт beta-токен из параметра auth и использует его для /api/v1/mcp. Проверки выполняются от имени издателя ссылки, поэтому доступны другие его datasets, названия чатов и поисковые фрагменты.

Ссылка → beta → owner identity → MCP → list/retrieval всех доступных владельцу datasets.

Кто и при каких условиях

Нужен действующий beta-токен и доступ к MCP API. Отдельная учётная запись не нужна. Граница — права издателя, а не вся платформа.

Что ограничивает вывод

Есть ownership-проверки, но они получают identity владельца; это не защищает границу публичного sharing. Runtime-воспроизведение не выполнялось.

Применимость к вашей лаборатории

В лаборатории /api/v1/mcp закрыт Nginx. Механизм присутствует в upstream-снимке; исполнение образа не проверено. Остальные beta-маршруты всё равно требуют отрицательных тестов.

Исправление / компенсация

Сразу закрыть API MCP и standalone MCP для beta-токенов. Для sharing выпускать отдельные токены с app/resource scope, разрешёнными операциями, сроком и отзывом. Не превращать их в обычную identity владельца.

F02 · HighCWE 863 · уверенность: высокая по коду

Отключение аккаунта не отзывает API/beta-доступ

При деактивации меняются IsActive и идентификатор веб-сессии. API/beta-ключи остаются в БД, а их resolver проверяет лишь непустой AccessToken и продолжает принимать отключённого пользователя.

Deactivate → IsActive=0 + INVALID_… → прежний API/beta key → owner identity → разрешённые ранее ресурсы.

Кто и при каких условиях

Бывший пользователь или держатель старого ключа с доступом к сервису. Сохраняются прежние права чтения, изменения и выполнения; произвольный чужой tenant не доказан.

Что ограничивает вывод

Свежий вход по паролю запрещается, старые веб-сессии инвалидируются; исключение касается API/beta. Runtime-воспроизведение не выполнялось.

Применимость к вашей лаборатории

Тот же механизм проверен в исходниках lab/upstream. Закрытая регистрация не решает отзыв ранее выданных ключей.

Исправление / компенсация

Проверять active/deleted-состояние в общем resolver для всех типов credentials. При offboarding отдельно удалять/отзывать API и beta-ключи и проверять повторный запрос каждым из них.

F03 · MediumCWE 863 · уверенность: высокая по коду

DISABLE_PASSWORD_LOGIN не блокирует парольный вход

Настройка читается из env/YAML и возвращается в system/config, но routed LoginByEmail её не проверяет: правильный пароль по-прежнему даёт сессию.

DISABLE_PASSWORD_LOGIN=true → config response; POST auth/login → проверка пароля → новый токен.

Кто и при каких условиях

Нужен действующий или подобранный пароль при включённом запрете. Вход без credentials не доказан. В OSS нет встроенной реализации OAuth/SSO.

Что ограничивает вывод

Проверка пароля и IsActive существует. Нельзя считать эту настройку реализованной политикой аутентификации. Runtime-воспроизведение не выполнялось.

Применимость к вашей лаборатории

В лаборатории false: сам запрет не запрошен. Дефект механизма есть и в upstream; нельзя использовать флаг как будущую защиту.

Исправление / компенсация

Добавить проверку на сервере до парольной аутентификации. До исправления реализовать политику на identity-aware gateway, закрыть обходные backend-порты и проверить отдельный административный recovery-путь.

func (s *UserService) LoginByEmail(ctx context.Context, req *EmailLoginRequest) (*entity.User, common.ErrorCode, error) {
	user, err := s.userDAO.GetByEmail(ctx, dao.DB, req.Email)
	if err != nil {
		common.Error("user not found by email", err)
		return nil, common.CodeAuthenticationError, fmt.Errorf("email: %s is not registered", req.Email)
	}

	decryptedPassword, err := common.DecryptPassword(req.Password)
	if err != nil {
		return nil, common.CodeServerError, fmt.Errorf("fail to crypt password")
	}

	if user.Password == nil || !s.VerifyPassword(*user.Password, decryptedPassword) {
		return nil, common.CodeAuthenticationError, fmt.Errorf("email and password do not match")
	}

	if user.IsActive == "0" {
		return nil, common.CodeForbidden, fmt.Errorf("this account has been disabled, please contact the administrator")
	}

	// Generate new access token
	token := common.GenerateToken()
	user.AccessToken = &token
	now := time.Now().Truncate(time.Second)
	user.LastLoginTime = &now

	if err = s.userDAO.Update(ctx, dao.DB, user); err != nil {
		return nil, common.CodeServerError, fmt.Errorf("failed to update user: %w", err)
	}
	if billingService := billing.Get(); billingService != nil && billingService.Enabled() {
		billingService.SyncLoginTokenRateLimit(ctx, user.ID, token)
	}

	return user, common.CodeSuccess, nil

F04 · MediumCWE 613 · уверенность: высокая по коду

Сброс пароля администратором сохраняет старую сессию

Admin ChangePassword записывает только новый password hash. AccessToken остаётся прежним; украденная подписанная сессия проходит последующую проверку БД.

Admin reset → hash changed → прежний AccessToken → ResolveAccessToken → старая сессия принята.

Кто и при каких условиях

Атакующий уже владеет действующей сессией, когда администратор меняет пароль. Доступ ограничен оставшимся сроком сессии: максимум 24 часа либо до другого события отзыва.

Что ограничивает вывод

Logout и активный self-service путь смены пароля ротируют AccessToken. Подпись и ограничение 24 часа продолжают работать. Runtime-воспроизведение не выполнялось.

Применимость к вашей лаборатории

Тот же кодовый механизм проверен в upstream. Изменение bootstrap-пароля в .env также не меняет существующую учётную запись.

Исправление / компенсация

Атомарно менять session identifier/auth epoch вместе с административным сбросом. В incident recovery отдельно отзывать API/share-ключи, поскольку это другие credentials.

func (s *Service) ChangePassword(ctx context.Context, username, newPassword string) error {
	userList, err := s.userDAO.ListByEmail(ctx, dao.DB, username)
	if err != nil || len(userList) == 0 {
		return fmt.Errorf("user '%s' not found", username)
	}

	if len(userList) > 1 {
		return fmt.Errorf("exist more than 1 user: %s", username)
	}

	user := userList[0]

	decryptedPassword, err := common.DecryptPassword(newPassword)
	if err != nil {
		return fmt.Errorf("failed to decrypt password: %w", err)
	}

	if user.Password != nil && common.CheckWerkzeugPassword(decryptedPassword, *user.Password) {
		return nil
	}

	hashedPassword, err := common.GenerateWerkzeugPasswordHash(decryptedPassword)
	if err != nil {
		return fmt.Errorf("failed to hash password: %w", err)
	}

	user.Password = &hashedPassword

	if err = s.userDAO.Update(ctx, dao.DB, user); err != nil {
		return fmt.Errorf("failed to update user: %w", err)
	}

	return nil

F05 · MediumCWE 668 · уверенность: высокая по коду

api.host и admin.host не ограничивают bind

Оба поля парсятся, но серверы строят адрес только из порта: :9380 / :9381. Это wildcard-listener, даже если в YAML указать 127.0.0.1.

YAML Host → config → Host отброшен → net.Listen / ListenAndServe на :port.

Кто и при каких условиях

Нужен сетевой доступ к хосту/контейнерной сети и расчёт оператора на host-binding. Это расширение поверхности, а не самостоятельный обход пароля.

Что ограничивает вывод

Container port mapping и firewall продолжают работать. Host отдельного standalone MCP используется корректно. Runtime-воспроизведение не выполнялось.

Применимость к вашей лаборатории

В lab наружу опубликован только 127.0.0.1:18080. Но admin.host:127.0.0.1 внутри контейнера не мешает другим контейнерам backend-сети обратиться к 9381.

Исправление / компенсация

Исправить оба listener через net.JoinHostPort. До этого закрыть прямую публикацию 9380/9381, ограничить межконтейнерный доступ и ingress firewall. Не заменять сетевую политику полем Host.

F06 · MediumCWE 295 · уверенность: высокая по коду

Elasticsearch HTTPS не проверяет сертификат

Общий ES transport содержит InsecureSkipVerify:true. Переключение es.hosts на https:// само по себе не проверяет CA и имя сервера.

es.hosts + credentials → HTTPS client → непроверенный TLS peer → документы, поисковые запросы и Basic credentials.

Кто и при каких условиях

Нужна возможность перехвата/подмены сетевого пути до ES при HTTPS. Компрометация без такой позиции не утверждается.

Что ограничивает вывод

Пароль ES включён. Он не защищает от подмены сервера или чтения незашифрованного трафика. Runtime-воспроизведение не выполнялось.

Применимость к вашей лаборатории

В lab ES работает по HTTP в закрытой сети: этот TLS-путь не активен, но шифрования трафика тоже нет. Исходный TLS-код идентичен между копиями.

Исправление / компенсация

Включить проверку цепочки/hostname и поддержку доверенного CA в клиенте. До исправления — проверенный mTLS tunnel/sidecar на доверенной границе и жёсткая изоляция сети.

F07 · MediumCWE 295 · уверенность: высокая по коду

MinIO HTTPS по умолчанию может не проверять сертификат

Go parser задаёт Verify=false. Если включить только minio.secure:true и не указать verify, transport получит InsecureSkipVerify=true; комментарий шаблона про default true не совпадает с кодом.

secure=true + verify omitted → Verify=false → InsecureSkipVerify=true → доверие подменённому object storage.

Кто и при каких условиях

Нужен HTTPS с пропущенным/false verify и атакующий на сетевом пути. Это условный дефект безопасного значения по умолчанию.

Что ограничивает вывод

Явное verify:true работает; для lab не заявляется активная TLS-уязвимость. Runtime-воспроизведение не выполнялось.

Применимость к вашей лаборатории

В lab явно verify:true, поэтому этот default исключён; secure:false означает HTTP. Конфиг parser/transport идентичен между снимками.

Исправление / компенсация

Явно задать secure:true и verify:true, установить доверенный CA. Исправить default Verify на true и тестировать отсутствующий параметр.

Модель угроз

RAGFlow обрабатывает недоверенные файлы и текст, хранит производные копии корпоративных данных и может выполнять действия через модели, инструменты и код. Его backend identity и сетевые credentials дают больше полномочий, чем отдельному читателю документа или получателю публичной ссылки.

Защищаемые активы

  • Оригиналы, chunks, embeddings, индексы, чаты, память и provenance.
  • User/team permissions, API/share keys, signing secret, model/connector credentials.
  • Control plane, host/VM, object buckets, backups и журналы.
  • Доступность CPU/RAM/disk/очередей и бюджет внешних providers.

Предположения и инварианты

  • Атакующий не имеет admin/root заранее; он может владеть документом, share token, обычной или ранее отключённой учёткой.
  • Resource ACL проверяется сервером после выбора итогового объекта; prompt не даёт дополнительных прав.
  • Изоляция tenant в UI не равна изоляции БД/индекса/worker/host. Для взаимно недоверенных групп предпочтительны отдельные инстансы и state credentials.
  • LLM, tools, MCP, парсеры и источники содержимого не считаются доверенными policy engines.

Риск переноса прав: исходная ACL коннектора не обязательно воспроизводится на каждый поисковый запрос к уже скопированным данным. До загрузки корпоративных источников необходимо выбрать модель авторизации: отдельные datasets/instances по группе доступа либо проверяемая синхронизация document ACL на query path. Полная end-to-end source ACL в этом обзоре не доказана.

Prompt injection и poisoning — сценарии, а не автоматически подтверждённые уязвимости. Практический тест: вредоносный текст пытается заставить агента выбрать чужой dataset, передать контекст внешнему URL или вызвать действие. Успехом защиты считается отказ policy/tool/network boundary, даже если модель следует тексту. «Добавить запрет в system prompt» недостаточно.

Как захарденить развёртывание

На схеме — предлагаемые границы. Стрелка означает разрешённый поток; каждая требует отдельной identity, сетевой политики и наблюдаемого отказа. Это целевая архитектура, не описание уже выполненных изменений.

Изоляция исполнения

Local provider исполняет код с полномочиями приложения. Self-managed Manager имеет privileged и Docker socket: no-new-privileges не убирает право управлять Docker. Я рекомендую отдельный execution host с Runner без app secrets, host mounts и сетевого доступа. Для SSH нужен отдельный непривилегированный account, проверяемый known_hosts и OS/cgroup isolation; сам SSH не является sandbox. Cloud provider добавляет внешнего получателя кода/данных и требует отдельной оценки политики.

Единый механизм полномочий

F01–F04 показывают разрыв между типом credential, состоянием аккаунта и итоговой identity. Сначала нужны локальные исправления: reject beta at MCP, active-user gate, backend login policy, revoke sessions on admin reset. Затем — typed principal/capability, который хранит token kind, resource scope, allowed actions, expiry и auth epoch и не допускает превращения share-token в неограниченного owner. Сравнение вариантов, миграция и tradeoffs приложены в hardening.md и проекте identity/capabilities. Никакой вариант здесь не реализован.

Что осталось непроверенным

  • Текущие контейнеры, итоговый env/rendered YAML, registry provenance и соответствие binary локальному commit.
  • Реальная доступность портов из разных сегментов, валидность TLS, OS firewall и network policies.
  • Полный маршрут document ACL от источников, все API authorization variants, XSS/rendering и connector OAuth.
  • Все native parser families, malformed files, decompression bombs, полный dependency/container CVE scan и external sandbox source.
  • Production backup restore, RPO/RTO, end-to-end audit/alert delivery и нагрузочные лимиты.

Полное coverage не заявлено. Архитектурное чтение и поисковые совпадения не считаются завершённым аудитом всех затронутых файлов. Независимый baseline и auth-проход использовали доступные 3 worker slots; число workers не является мерой покрытия.
