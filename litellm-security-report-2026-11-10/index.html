Мы можем сохранить единый proxy для доверенных команд, если изоляция подтверждена тестами и последствия компрометации приемлемы. Для разных классов чувствительности или взаимно недоверенных арендаторов я рекомендую отдельные экземпляры с разными provider keys, БД/Redis и workload identity. Это уменьшает общий радиус поражения ценой дополнительных ресурсов, обновлений и мониторинга; влияние на задержку здесь не измерялось.

Модель угроз

Что защищаем и кому доверяем

Основные активы — provider credentials и бюджеты, master/admin authority, prompts и ответы, загруженные файлы, identities/tenant permissions, конфигурация, DB/Redis и сам runtime. Даже при шифровании ключей в БД живой процесс получает открытые credentials для вызова провайдеров. Поэтому права pod/VM и исходящая сеть входят в модель защиты.

Инварианты, которые должны выдерживать обновления

  • Идентичность определяет роль, модели, tenant и доступ к каждому объекту; client metadata не становится доверенным identity.
  • Provider credential отправляется только утверждённому получателю; ни URL fetch, ни callback, ни fallback не дают доступ к внутренней сети по умолчанию.
  • Лимиты действуют во всех workers и replicas; поведение при потере БД/Redis/IdP выбрано заранее.
  • Данные сохраняются только в согласованных sinks с известными TTL, retention и правами; encryption credentials не означает encryption всех логов.
  • Конфиг, hooks, custom auth, MCP stdio и процесс развертывания имеют административную степень доверия.

Сценарии для проверки

Следующие сценарии — модель угроз и deployment risks, а не список новых найденных CVE. Приоритет учитывает потенциальный ущерб; реальная достижимость зависит от включённых features и сетевой доступности.

ID / областьСценарий и предпосылкиПоследствияКонтроли и остаточный риск
T1 · SpoofingУтечка workload/master key, permissive JWT audience, доверие поддельным identity headers.Чужая identity, admin-доступ, расходы.Scoped keys, issuer+audience, header sanitation, закрытый backend; токен остаётся bearer secret.
T2 · TamperingПользователь подставляет чужой response/file/vector-store ID, модель или fallback.Cross-tenant доступ, обход model policy.Ownership на каждой операции, явные grants, deny-by-default для нужных capabilities, тесты A/B.
T3 · SSRF / disclosureURL контента, api_base, fallback, callback или OpenAPI spec уводит запрос в нежелательный адрес.Внутренние сервисы, metadata, credentials у другого получателя.URL validation и ограничения overrides плюс независимый egress. Проверять каждый включённый fetch path.
T4 · Elevation / executionДоступ к config/hook/stdio/custom-code guardrail или вредоносный image.Выполнение с правами процесса, кража секретов и lateral movement.Контроль admin/config, подписи и digest, non-root, минимальные IAM/mounts, разделение tool runtime.
T5 · Information disclosurePrompts, ответы, токены или headers сохраняются в callback/error/trace/cache/backup.Вывод данных за trust boundary, длительное хранение.Минимизация всех sinks, canary-тесты, TLS, storage encryption и ACL. Regex masking неполон.
T6 · DoS / denial of walletВысокая параллельность, batch/streaming, большие bodies, retries и медленные providers.Исчерпание памяти/соединений/LLM бюджета.Edge caps, admission queue, shared Redis, pricing, fail-closed там, где требуется, provider quota. Возможен overshoot при async учёте.
T7 · Browser/sessionXSS на UI origin, unsafe CORS или неверный внешний scheme за ingress.Угон JS-readable session bearer, изменение конфигурации.Выделенный HTTPS UI origin, закрытый доступ, Secure cookies, минимальные scripts, корректный PROXY_BASE_URL.
T8 · RepudiationОбщий admin credential, отсутствующие app audit logs или mutable SIEM.Невозможность установить автора и масштаб изменения.Персональные identities, app audit в EE, отдельный append-only sink; в OSS инфраструктурный аудит имеет меньшую полноту.
T9 · Shared stateКомпрометация или отказ DB/Redis, stale auth/JWKS cache, потерянный salt.Изменение policy, задержка отзыва ключей, обход лимитов или потеря credentials.TLS/ACL/backup, общий coordination Redis, TTL и outage/revocation drills, сохранение salt. Root/process compromise обходит field encryption.
T10 · LLM/tool boundaryPrompt injection через RAG/tool output или provider response побуждает agent выполнить действие.Эксфильтрация, опасные tools, неверные бизнес-операции.Guardrails как дополнительный слой; authz в tool executor, sandbox, user approval для опасных действий, валидация output в приложении.

Пять различий, которые нельзя потерять при настройке

Auth и сеть

Master-key boot gate не проверяет всю криптографическую стойкость ключа. JWT signature без нужных issuer/audience не подтверждает, что токен выдан именно нашему gateway. CORS не запрещает запросы из backend-клиентов.

Два вида Redis

Общий coordination Redis нужен для распределённого состояния. Response cache отдельно хранит результат модели и может оставаться выключенным. Router state тоже должен иметь общую конфигурацию.

Пустой allowlist

У model grants пустые списки могут означать все доступные модели или наследование. У allowed_file_extensions=[] по документации смысл обратный: запрет uploads. У object permissions семантика зависит от capability и deny-by-default флага.

Шифрование и redaction

Шифруются отдельные credential values. Логи, prompts, cache и backups требуют собственной защиты. В коде присутствуют legacy XSalsa20-Poly1305 и опциональный AES-GCM; смена алгоритма не означает миграцию старых записей.

Значения из DB/UI и environment могут менять эффективную конфигурацию; precedence отличается по настройке. Например, env prompt-storage может включить хранение независимо, а файлом владеющие settings имеют отдельную логику overrides. После rollout проверять поведение и сохранённые данные. Не выгружать полный конфиг с секретами в CI или тикет.

Gate доставки

  1. Выбрать поддерживаемую release-ветку с нужными исправлениями и features. Не деплоить main, dev/rc или mutable latest/main-stable как неконтролируемое обновление.
  2. Проверить signature доверенным публичным ключом, зафиксированным по immutable commit и fingerprint. Проверить digest выбранного image и именно его отправить во внутренний registry.
  3. Сохранить SBOM, dependency locks/hashes, результат SCA/image scan и provenance. Сканы известных CVE не обнаруживают автоматически любой malware.
  4. Проверить container содержимое и запуск без production secrets на стенде с контролем сети, затем выполнить acceptance-тесты из отчёта.
  5. Продвигать тот же digest между средами; admission policy должна блокировать непроверенные образы, а не просто неизвестные tags.
Если запускался заражённый артефакт. Изолировать workload/host, сохранить доказательства и привлечь IR. Чистое пересоздание image/venv/host предпочтительнее «обновления на месте». Ротировать доступные provider/master/virtual/DB/cloud credentials и проверить использование за пределами инфраструктуры. В подозрительном окружении сначала не запускать Python/pip: Python startup hooks могут повторно выполнить payload. Отсутствие временных marker-файлов не доказывает чистоту. Подробности и границы затронутых артефактов — в официальных incident reports выше.

Проверка подписи как шаблон CI

Команды не выполнялись в рамках обзора. Подставить проверенный release digest. Public key брать из доверенного baseline, а не из того же непроверенного image. Подпись — один из gates, а не замена анализа происхождения.

# Документированный SHA-256 файла ключа
# e3fe3e08c44b16407fe0b37c43b4f8b603b3a0f4ee74c29e647bc022d762c2c0

shasum -a 256 ./cosign.pub
cosign verify --key ./cosign.pub \
  'ghcr.io/berriai/litellm@sha256:<reviewed-digest>'

# На фактически запущенных Pod проверить status.containerStatuses[].imageID
# На VM сверить container image digest и Config.User

Развёртывание · Kubernetes

Проверять результирующий Pod, сеть и права

Python chart helm/litellm-helm и отдельный split/Rust chart helm/litellm имеют разные компоненты и настройки. В этом отчёте основа — Python Proxy. Default values первого chart оставляют security contexts пустыми и разрешают service-account automount. Их нельзя принимать как hardened baseline.

Сначала выполнить helm template на выбранной версии и ваших values, затем проверить результирующие Deployment/Job/Service/Ingress. Настройки из примера ниже передаются в соответствующие поля chart или patch, а не целиком в произвольный values.yaml. В основном Dockerfile этого snapshot runtime объявлен как USER root; имя образа и Helm values недостаточны, чтобы считать процесс non-root.

Pod spec: направление hardening
spec:
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: litellm
      image: ghcr.io/berriai/litellm-non_root@sha256:<reviewed-digest>
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      resources:
        requests:
          cpu: "500m"
          memory: "1Gi"
        limits:
          cpu: "2"
          memory: "2Gi"
      env:
        - name: LITELLM_NON_ROOT
          value: "true"
        - name: XDG_CACHE_HOME
          value: /app/cache
        - name: PRISMA_BINARY_CACHE_DIR
          value: /app/cache/prisma-python/binaries
        - name: LITELLM_MIGRATION_DIR
          value: /app/migrations
      volumeMounts:
        - name: tmp
          mountPath: /tmp
        - name: cache
          mountPath: /app/cache
        - name: migrations
          mountPath: /app/migrations
        - name: config
          mountPath: /app/config.yaml
          subPath: config.yaml
          readOnly: true
  volumes:
    - name: tmp
      emptyDir:
        medium: Memory
        sizeLimit: 128Mi
    - name: cache
      emptyDir:
        sizeLimit: 256Mi
    - name: migrations
      emptyDir:
        sizeLimit: 128Mi
    - name: config
      configMap:
        name: litellm-config

Проверить числовой UID/GID выбранного image и права на writable volumes; при необходимости явно задать проверенные runAsUser/runAsGroup/fsGroup. Не переносить UID из другого image или QA compose. LITELLM_NON_ROOT=true — сигнал приложению, права обеспечивает runtime. Ограничения readOnlyRootFilesystem и noexec надо проверить с реальной Prisma migration/toolchain: не открывать весь filesystem ради одного пути.

Особенности Python Helm chart. Шаблон собирает image как repository:tag; неизвестное поле image.digest не следует считать работающим. Для pinning можно проверить отрендеренное repository:release-tag@sha256:digest либо patch итогового image. serviceAccount.automount применяется к ServiceAccount только при его создании chart; с существующим SA и на уровне Pod проверять эффективный automount отдельно. Источники: deployment.yaml:46–56, serviceaccount.yaml:1–13.

Сеть и identity

Мы ограничиваем вход только ingress-controller и утверждёнными внутренними клиентами, исходящий трафик — DB, Redis, DNS, IdP/secret store, approved providers и sinks. При использовании egress proxy прямой выход нужно запретить, иначе переменные HTTP_PROXY не создают обязательной границы. Доступ к metadata, Kubernetes API и node services проверять с учётом CNI и облачной платформы.

NetworkPolicy: отправная точка default-deny
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: litellm-default-deny
  namespace: llm
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: litellm
  policyTypes: ["Ingress", "Egress"]
  ingress: []
  egress: []

# ДО применения нужны отдельные разрешающие policies:
# - ingress от конкретных ingress-controller pods
# - DNS TCP/UDP 53 к kube-dns/CoreDNS
# - PostgreSQL и Redis к конкретным адресатам и портам
# - контролируемый egress proxy или approved private endpoints
# - IdP/secret manager/observability, если используются
#
# Обычная NetworkPolicy не реализует FQDN allowlist.
# Проверить поддержку CNI, IPv6, hostNetwork/node/metadata paths.
# Не добавлять allow 0.0.0.0/0 как замену списка providers.

ServiceAccount не должен иметь cluster-admin, создавать Pods или читать чужие Secrets. Если нужны IRSA/Workload Identity или JWT-аутентификация, заменить безусловный отказ от token mount на минимальный projected token с нужной audience и коротким сроком, затем проверить RBAC и trust policy. Это осознанное исключение, а не причина оставить стандартный широкий token.

Data stores и миграции

Отдельные DB/user/schema и Redis namespace/ACL для prod, stage и разных зон доверия. Проверить TLS verification, резервные копии и доступ администраторов к ним. Runtime-роль минимизировать; миграции требуют DDL, поэтому разделение migration job и runtime credentials надо подтвердить возможностями выбранного image/chart. Не отзывать DDL до проверки startup-поведения.

Secrets не должны попадать в ConfigMap, Helm values в Git, helm template logs или debug dump. Kubernetes Secrets требуют encryption at rest в control plane и ограниченного RBAC. В Pod монтировать только нужные secret references. Для HA проверить согласованность конфигурации и отзыв ключей на всех replicas, PDB, rollout и нагрузку на DB/Redis.

Развёртывание · VM

Тот же trust boundary без Kubernetes

Для VM я рекомендую выделенный service account ОС, отдельный host или изолированный container, bind backend на loopback/private interface и TLS reverse proxy. Firewall запрещает обход к порту 4000 и исходящий доступ к лишним сетям. Экземпляр не должен наследовать SSH/CLI credentials администратора и широкую instance IAM role.

Профиль container runtime
# Шаблон аргументов container runtime, не команда готового deployment.
# Выбрать и проверить non-root image, числовые UID/GID и права volumes.
# Значения secrets держать в управляемом secret store либо в root-readable
# env-файле с минимальными правами. Не добавлять секреты в shell history.

--publish 127.0.0.1:4000:4000
--read-only
--cap-drop ALL
--security-opt no-new-privileges:true
--pids-limit 256
--memory 2g
--cpus 2
--tmpfs /tmp:rw,noexec,nosuid,nodev,size=128m
--mount type=bind,src=/etc/litellm/config.yaml,dst=/app/config.yaml,readonly

# /app/cache и /app/migrations: отдельные ограниченные writable volumes,
# права под проверенный UID/GID, noexec где совместимо с toolchain.
# Нет Docker socket, host network, SSH home, kubeconfig или host root mount.
# Outbound firewall/egress proxy и HTTPS reverse proxy задаются отдельно.

При запуске через systemd использовать отдельный User/Group, NoNewPrivileges=yes, PrivateTmp=yes, ProtectSystem=strict, ProtectHome=yes и узкие writable directories. Проверить совместимость с toolchain и процессной моделью. Не выполнять обновление package/image от имени рабочего процесса, зависимости собирать заранее. File encryption и filesystem ACL не защищают secrets от процесса, которому они нужны для работы.

Ограничение API на edge

Ниже пример двух разрешённых inference routes. Его нужно адаптировать к реальным aliases, streaming, WebSocket и clients; остальной API требует отдельного решения. Внешние identity headers нужно удалять либо заменять только доверенным auth proxy. При нескольких hops корректно восстановить клиентский адрес на каждом доверенном участке.

Пример nginx route allowlist
# Фрагмент nginx внутри HTTPS virtual host клиентского API.
# TLS, auth сети, connection/rate limits и upstream объявляются отдельно.
client_max_body_size 8m;
client_body_timeout 15s;

location = /v1/chat/completions {
    proxy_pass http://litellm_backend;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 120s;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto https;
}
location = /v1/embeddings {
    proxy_pass http://litellm_backend;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto https;
}
location / { return 403; }

# Добавлять /v1/messages, /v1/responses, WebSocket и aliases
# только когда они нужны и проверены.
# UI/management доступны через отдельный защищённый ingress.

Административный доступ оставить через VPN/bastion/SSO, отдельные аккаунты и restricted hostname. DISABLE_ADMIN_UI не закрывает management API. DB/Redis не публиковать в интернет. Их TLS/ACL, backup, обновление и мониторинг такие же обязательные, как для Kubernetes. Для действительно недоверенных tenant нужен отдельный runtime и credentials, а не только отдельный hostname.

Минимальный отрицательный smoke test

Пример для staging. BASE_URL — ваш тестовый gateway, model alias должен существовать. Заголовки с тестовыми секретами не выводить в CI logs. Ожидается auth-отказ и отсутствие provider call; конкретный код 401/403 зависит от пути и версии.

# Без Authorization, тело синтаксически корректно
curl -sS -o /dev/null -w '%{http_code}\n' \
  "$BASE_URL/v1/chat/completions" \
  -H 'Content-Type: application/json' \
  --data '{"model":"approved-chat","messages":[{"role":"user","content":"auth-check"}],"max_tokens":1}'

# Все три docs поверхности надо проверять отдельно
curl -sS -o /dev/null -w '%{http_code}\n' "$BASE_URL/"
curl -sS -o /dev/null -w '%{http_code}\n' "$BASE_URL/redoc"
curl -sS -o /dev/null -w '%{http_code}\n' "$BASE_URL/openapi.json"

# Зафиксировать imageID работающих контейнеров без выгрузки env/secrets
kubectl -n llm get pods -l app.kubernetes.io/name=litellm \
  -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.status.containerStatuses[*].imageID}{"\n"}{end}'

Что мониторить постоянно

Identity и изменения

Admin logins, failed login bursts, новые ключи/роли/teams, создание MCP/callback/model endpoint, включение clientside overrides, изменения конфигурации и network policies, срок действия credentials.

Runtime и данные

Неожиданный outbound DNS/HTTP, secret access, 401/403/429/503, Redis/DB failures, отсутствие audit/spend событий, рост token spend и retry count, OOM, длинные streams, изменения image digest и writable paths.

Настроить alerts на provider-side расходы и использование ключей за пределами gateway. Проверять, что redaction не уничтожила нужные для расследования request IDs, actor, route, объект и outcome. Полные prompts для такого аудита обычно не нужны.

Переход к отдельным экземплярам для разных зон данных требует отдельных DB/Redis/keys и, при необходимости, provider projects/accounts. Мы выигрываем в containment, но получаем больше state, обновлений и capacity planning. Такой переход делать после инвентаризации tenants и требований к данным; общего экземпляра достаточно только там, где приняты shared-admin и shared-runtime риски.

Рассмотренные поверхности

Проведены независимые статические проходы по модели архитектуры, auth/config boundaries и сетевым/логирующим настройкам. Полностью просмотрены 27 уникальных файлов выбранных auth/URL/middleware/config путей. Крупные proxy_server.py, _types.py, user_api_key_auth.py, litellm_pre_call_utils.py, ui_sso.py и документация проверялись по релевантным функциям и вызовам; весь файл или репозиторий этим не покрыт.

Не выполнен полный аудит provider integrations, exporters, MCP/agents, Rust gateway, UI bundle, dependency tree, CI/release pipeline и всех management endpoints. Не проверялись реальная лицензия, manifests/VM config, настройки clouds, runtime/network traces, redaction каждого API и attack-path воспроизведение. Загрузка дополнительных файлов в локальный checkout не означает, что они автоматически были проаудированы.

После завершения загрузки дополнительно проверены consumers prompt-storage и audit-license gate, полностью просмотрены telemetry consent/settings и проверены привязки securityContext, image и ServiceAccount в Python Helm templates. Это уточняет отдельные параметры, но не заменяет тесты реального rendered deployment.

Существенные расхождения и осторожность с документацией

  • Общая формулировка SECURITY.md про отсутствие self-hosted telemetry шире, чем актуальная страница о явно включаемой usage telemetry. Проверять конкретный механизм и флаги, не выводить отсутствие egress из факта self-hosting.
  • Описание шифрования в FAQ ориентируется на SecretBox, а код также содержит выбор AES-GCM и отдельные bearer-token helpers. Нельзя выводить whole-database encryption из списка credential helpers.
  • Docs требуют user_url_validation под litellm_settings, текущий код принимает его и в отдельных general/DB путях. Для переносимости использовать документированное расположение.
  • Документированное описание forwarded trust нельзя распространять на все IP-проверки: allowed_ips, OAuth2-proxy и MCP используют разные пути. Прямой backend нужно закрыть, headers очистить на edge.
  • Body caps видны в документации как настройки, но рассмотренный middleware применяет общий operator cap только при premium_user. Проверить свою редакцию.
  • OWASP mapping в репозитории помечен как проверенный против более старой версии 1.104.0 и содержит исторические ограничения. Его сведения об API redaction/guardrails использовать как тестовые вопросы, а не как автоматически актуальные finding против этого commit.
  • general_settings.database_url описан в схеме, но в просмотренном lifespan конкретное подключение берёт DATABASE_URL. Полная precedence CLI/startup не установлена; пример baseline использует env reference.

При сборке служебного индекса Codex Security клонирование ещё не завершилось, поэтому его launch metadata записаны как unversioned directory snapshot.
