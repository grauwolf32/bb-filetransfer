Мой выбор для вашего сценария

Haystack + существующий Elasticsearch, со статическим retrieval pipeline

Я бы начал с Haystack для ingestion и hybrid retrieval, одного Elasticsearch для текста и векторов и небольшого API под вашим контролем. Из решения нужно исключить агенты, Code execution, MCP, пользовательские pipeline YAML и редакторы исполняемых шаблонов. Это уменьшает поверхность, которая вам не нужна, а не обещает отсутствие RCE.

В проверенном adapter BM25 и dense retriever объединяются через библиотечный DocumentJoiner. Отдельная vector DB и Elasticsearch server-side RRF для этого пути не требуются. [1] [2] Если corpus и pipeline совсем простые, тот же дизайн можно реализовать напрямую через официальный client — это ещё меньше framework, но больше собственной ответственности за lifecycle и проверки.

Это не drop-in приложение. Haystack и LlamaIndex — библиотеки. Авторизация, upload API, очередь/повтор jobs, UI, audit и эксплуатация принадлежат вашему сервису. Если принципиален готовый интерфейс без разработки, ближе Kotaemon; его я рассматриваю как пилотный кандидат после hardening, а не как автоматически безопасную production-замену.

Выбор по ограничениям

Для retrieval не нужна вся RAG-платформа

Под «RAG» здесь принимается ваш узкий набор: подготовить текст, разбить на chunks, вычислить embeddings, найти релевантные фрагменты и вернуть их с provenance. Генерация ответа LLM — отдельная необязательная стадия. Без неё не нужны chat model, agent loop, sandbox или выполнение tools.

НужноРеализацияНеобязательно для этого сценария
IngestionКонвертер выбранных форматов, deterministic chunking, embedding endpoint, bulk indexingUniversal connectors, OCR для каждого файла, GraphRAG и knowledge compilation.
Лексический поискES/OpenSearch BM25, корректные analyzers/multi-fields, поиск exact identifiersВторая full-text БД, если text уже в ES/OS.
Dense retrievalВ том же chunk index: text + vector + metadata/ACL/versionОтдельная Qdrant/Chroma, если ES/OS покрывает нужный ANN.

UI / answer generationПодключить только при реальной потребностиПлатформа агентов и shared beta credentials как побочный способ выдать search API.

Отсутствие отдельного SQL/queue сервиса возможно в простом пилоте, но job state, concurrent ingestion и ACL lifecycle всё равно должны где-то надёжно храниться. Filesystem/SQLite подходят не для любого режима и нагрузки.

Разбор кандидатов

Основной выборНе готовое приложение

Haystack + Elasticsearch / OpenSearch

Для статических indexing/query pipelines это хороший баланс между полностью своим кодом и большой платформой. Есть отдельные BM25, embedding и hybrid retrievers. Один document store может хранить chunks, metadata и dense vectors. В OpenSearch-варианте используется другой adapter, а не подмена URL в ES client. [1] [9]

Я рекомендую подключить только нужные converters/embedder/retrievers; build хранит заранее выбранный pipeline. Framework не заменяет authorization: request identity, mandatory filters, доступ к original download и право delete — ваша ответственность. Конструкторы/serialized pipelines не должны принимать пользовательские class paths или YAML. Это особенно важно с учётом открыто заявленной upstream trust model. [4]

Издержки: написать API/UI, durable ingestion state и ACL middleware, поддерживать совместимость core+integration+engine. Для query-only части не нужен PyTorch, если embeddings обслуживаются отдельным endpoint; parser/embedding dependencies можно оставить в worker. Это архитектурный вывод, экономия не измерялась. Telemetry можно отключить через HAYSTACK_TELEMETRY_ENABLED=False; сеть ограничить независимо. [8]

Самая узкая реализация

Небольшой API без RAG framework

Если задача стабильно сводится к upload/index/delete и lexical/vector/hybrid search, можно использовать официальный search client и свой небольшой ingestion worker. API на Go или Python получает только query и разрешённые business filters, формирует BM25 и ANN, объединяет ranks и возвращает chunks. Весь engine-level retrieval уже есть в ES/OS. [14] [19]

Сильная сторона — нет agent DSL, dynamic component registry или pipeline loading в публичном процессе. Но «меньше кода» не равно готовая безопасность: вы отвечаете за ACL обеих веток, indexing consistency, retries, citations и удаление устаревших chunks. При многих форматах и меняющихся pipelines Haystack экономит разработку. Я бы выбрал direct client только при действительно узком контракте и готовности команды владеть этим сервисом.

Альтернатива framework

LlamaIndex + Elasticsearch

Elasticsearch adapter поддерживает metadata filters, hybrid, deletion и сохранение текста; core MIT. Это подходящая основа, особенно если нужны document/node abstractions и команда уже работает с LlamaIndex. [10] [12] Но default adapter strategy — dense; HYBRID требует соответствующей стратегии. Проверенные query filters имеют precedence над es_filter, что важно при попытке использовать его как неизменяемую ACL. [11]

Я бы ставил core и конкретные integrations, не подключал query engines с eval/text-to-SQL/tools и не принимал custom_query от клиента. Полного security-сравнения всех adapters не проводилось; исторический safe_eval RCE тоже был у этой экосистемы. Выбор по реальным путям важнее выбора бренда. [13] Для server-side hybrid нужно отдельно проверить helper strategy и доступность engine features; generic галочка «Hybrid» этого не доказывает.

Готовый UI

Kotaemon

Из готовых UI это ближе к document-QA: загрузка, источники, PDF preview, hybrid pipeline. Elasticsearch поддержан как full-text docstore; vectors в проверенной конфигурации идут в отдельный store. Значит, у ES-варианта остаются два индекса и задача согласованного обновления/удаления. [22] [24]

Проверенный flowsettings.py содержит dev mode, fallback admin credentials и список ReAct/ReWOO/GraphRAG возможностей. Эти настройки нужно пересмотреть, а не наследовать. Это не новый подтверждённый RCE: startup/auth и пользовательские dataflows не аудировались. Для закрытого пилота можно оставить только простую QA pipeline, отключить ненужные index/reasoning types, заранее выбрать local providers и поставить gateway. [23] Поискать более маленький UI поверх вашего API иногда проще, чем сужать существующий app.

AnythingLLM

MIT, готовая загрузка и document chat; default LanceDB и несколько vector backends. В опубликованном списке не найден Elasticsearch, поэтому не считаю этот app готовым выполнением вашего требования Elastic+BM25. [26] Проверенный Compose с одним service содержит SYS_ADMIN и host gateway — количество контейнеров не отражает полномочия collector/browser/agent подсистем. [27]

Имеет смысл, если поиск по документам нужен преимущественно через chat, а ES и отдельный лексический интерфейс можно исключить. Тогда сравнивать нужно качество retrieval и permissions, а не только удобство установки.

Onyx

Это снова полноценная платформа. В просмотренном main уже OpenSearch, а также отдельные API/background/web/model services, Postgres/cache/object storage и optional MCP/webhook/code components. [28] Core вне ee — MIT, ee отдельно лицензирован. [29]

Рассмотрел бы при приоритете connector ecosystem и корпоративного knowledge assistant после проверки edition-specific controls. Для цели убрать массу и execution surface это не мой shortlist. Потребление ниже RAGFlow не измерялось и не обещается.

Open WebUI и Dify не включены в основной shortlist: они прежде всего приложения для chat/workflows, а задача здесь — узкий retrieval service. У текущего Open WebUI дополнительно есть branding terms; некорректно описывать его как просто прежний BSD без оговорок. [34]

Самая важная ловушка: retrieval filters ≠ ACL

Нельзя передать tenant-фильтр один раз в retriever constructor, разрешить клиенту filters и считать изоляцию готовой. В Haystack REPLACE может заменить init filters; MERGE тоже не гарантирует неизменяемую security condition. В LlamaIndex adapter непустые query.filters идут вместо es_filter. Это штатная семантика библиотек, опасной становится её неправильная интеграция. [2] [3] [11]

# Pseudocode: authorization owns the final predicate
principal = authenticate(request.credentials)
mandatory_acl = acl_for(principal)       # server-owned
business = parse_allowlisted_filters(request.filters)
effective_filter = AND(mandatory_acl, business)

bm25_hits = bm25(query, filter=effective_filter)
dense_hits = ann(embed(query), filter=effective_filter)
hits = rrf(bm25_hits, dense_hits)          # merge already scoped hits
return authorized_chunks_and_sources(hits)

# Never expose: raw query DSL, index names, custom_query,
# pipeline YAML, class paths, model download URLs, ACL keys.

Фильтровать только после top-k хуже: чужие кандидаты уже могут попасть в reranker/prompt/logs; кроме того, итоговых разрешённых результатов будет меньше. Для обоих branches нужны предикаты до выдачи кандидатов; повторная проверка перед generation/download полезна как дополнительная граница.

Как реально снизить риск RCE и утечки

Я бы менял достижимые возможности системы: убрал бы выполнение кода, агенты, импорт pipeline и сеть из parser-worker. Пересадка на другую марку RAG-системы без такого ограничения не даёт нужного результата.

У RAGFlow есть опубликованные RCE advisories, но их число не является сопоставимой метрикой риска. У Haystack тоже был template RCE CVE-2024-41950: advisory указывает affected ≤2.3.0 и patched ≥2.3.1. [5] Это не обвинение текущего Haystack, а основание исключить пользовательские executable definitions. Уязвимость парсера или зависимости остаётся возможной и при retrieval-only дизайне.

Парсинг: простые форматы сначала, OCR по необходимости

Для текстовых PDF/Markdown/TXT/простых DOCX достаточно узкого набора converters. Для таблиц, сложного layout и scans можно добавить Docling в isolated worker, а не во все query replicas. Код MIT, модели имеют отдельные licenses. [30] В Docling есть enable_remote_services=False, allow_external_plugins=False, document_timeout и artifacts_path. [31] Запрет external processing не блокирует отдельное скачивание weights — для offline нужен подготовленный cache и сетевой запрет. [32]

Не ставить universal parser/office/browser extras «на всякий случай». Если UI preview требует active HTML/SVG, отдавать его с отдельного origin и ограничениями, не из origin с credentials. Даже тонкий backend не исправит небезопасный preview.

Целевая архитектура

Минимальный логический набор: retrieval API, search engine, embedding runtime и отдельный batch/worker для ingestion. Embeddings могут жить внутри worker/API, но тогда модель дублируется в process replicas; общий endpoint уменьшает duplication и добавляет сетевую зависимость. Originals хранить в существующем управляемом хранилище; отдельный MinIO не обязателен, если он не нужен.

Hybrid: начать с простого RRF

Сначала сохранить явные режимы lexical, vector и hybrid. BM25 и ANN возвращают одинаково scoped кандидатов; RRF объединяет ranks, не складывает несопоставимые raw scores. Candidate depth, deduplication по chunk/document и конечный top-k нужно подбирать на ваших данных. Нейросетевой reranker добавлять только если выигрыш качества оправдывает latency и RAM.

Haystack client-side joiner — наш основной путь. Другой компонент, ElasticsearchInferenceHybridRetriever, использует server-side RRF и ELSER: не считать их взаимозаменяемыми по лицензиям и deployment. Для OpenSearch есть собственный hybrid/search pipeline и RRF; это отдельная конфигурация engine. [2] [17] [19] [20]

Версии и лицензии — отдельный acceptance gate

На дату просмотра release list Haystack показывал stable v3.4.1; source spot-check integrations сделан на зафиксированном main. Это не проверенная совместимая комбинация packages. [7] Для PoC нужно pin stable core + matching integration + client + engine, пройти retrieval/filter/TLS/delete regression и зафиксировать lockfile. Не копировать пример xpack.security.enabled=false из quickstart в инфраструктуру.

Откуда получится экономия ресурсов

Уменьшение стека — в первую очередь результат отказа от ненужных постоянно работающих подсистем и локальной chat generation. Elasticsearch/OpenSearch, embeddings и сложный PDF/OCR могут остаться основными потребителями RAM/CPU. Без измерений я не утверждаю, что Haystack быстрее LlamaIndex или что новый стек займёт конкретное число гигабайт.

Калькулятор только сырых FP32 embeddings

Формула N × dimensions × 4 bytes. Это не оценка общей RAM, RSS или disk ES. Не включены HNSW, quantized copies, original vectors, text/_source, inverted index, metadata, caches, replicas и merge workspace. Для 1 млн × 1024: 4,096 GB ≈ 3,815 GiB только raw FP32.

Quantization меняет память search representation, но конкретные defaults и доступные типы зависят от версии engine; original vectors и другие структуры могут храниться дополнительно. Сравнивать конфигурации нужно при одинаковом recall. [14]

Что использовать для embeddings

Для первого сравнения можно сохранить уже выбранную в лаборатории Qwen3-Embedding-0.6B через текущий local endpoint. Это убирает смену модели как переменную, но не объявляет её лучшей для вашего корпуса. Для Linux deployment TEI — возможный отдельный runtime; его README показывает эту модель. [33] На Mac не копировать CUDA container example; проверить архитектуру и поддерживаемый backend. Query/document preprocessing и инструкции должны совпадать с model contract.

Нужные измерения: idle/peak RSS отдельно по API, parser и model; batch throughput, cold/warm latency, disk/chunk, concurrency, reranker cost и время full reindex. «Работает в Docker» или минимальные RAM из README не являются сравнительным benchmark.

Пилот и перенос из RAGFlow

Я бы сравнил Haystack+ES с тонким ES client на одной тестовой коллекции, оставив одинаковые parser/chunking/model и ACL policy. OpenSearch — отдельная ветка решения, если его лицензия/эксплуатация важнее сохранения имеющегося ES. Готовый UI не должен менять engine comparison незаметно.

Порядок миграции

  1. Выделить требования: форматы/сканы/таблицы, объём chunks, QPS, группы доступа, need for UI/citations, latency и freshness. Не добавлять agent/tool requirements автоматически.
  2. Экспортировать originals и source metadata/ACL через разрешённый путь; зафиксировать dataset/document inventory. Секреты, beta/API keys и внутреннюю auth-модель RAGFlow не переносить.
  3. Создать новый versioned corpus/index со своей схемой. Повторная ingestion originals обычно надёжнее, чем объявить внутренний RAGFlow chunk index совместимым с новым adapter.
  4. Переиспользовать embeddings только при доказанном совпадении model revision, dimensions, preprocessing, normalization, instructions и chunk-to-source/ACL mapping. Одной одинаковой размерности недостаточно.
  5. Прогнать functional/ACL/delete/quality/resource gates; query traffic переключать через стабильный API или corpus alias. Исходную установку оставить доступной для контролируемого rollback без записи из нового сервиса в её индексы.
  6. После подтверждения полноты и retention-плана закрыть старые tokens/ingress и вывести ненужные сервисы. В этой работе миграция и остановка лаборатории не выполнялись.
Практическая рекомендация: не искать ещё один «всё-в-одном» продукт только ради замены RAGFlow. Начать с узкого retrieval backend и доказать quality + ACL + lifecycle. Если создание UI/API оказывается главным бюджетом, это основание пересмотреть выбор в пользу готового приложения — с отдельной оценкой его прав и defaults.

Предыдущий отчёт: безопасность вашей RAGFlow lab и 7 source-backed дефектов. Он не изменён этим сравнением.
