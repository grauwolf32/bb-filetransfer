00 / Ключевые выводы

Контролировать действия,
которые модель может совершить

MCP gateway выносит проверку доступа из агента в инфраструктуру. Его ценность — в управлении правами на вызов инструментов, делегации identity и едином аудите.

Главная рекомендация · аналитический вывод

Для крупной организации выбирать нужно архитектуру контроля tool access: gateway + корпоративный IAM + права в backend + изоляция runtime + принудительный маршрут. Набор текстовых guardrails следует оценивать как дополнительный слой. Фактическая граница защиты определяется тем, какие пути агент способен обойти.

01 / ПРАКТИКА

Централизация с ownership

Uber подробно описывает собственный gateway и управление включением tools. Cloudflare — централизованный remote MCP и контроль обходных подключений. S04S05

02 / IDENTITY

Человек и агент — две сущности

Нужно сохранить user context и отдельно определить workload/client. Иначе shared credential размывает персональные права и ответственность. S06S34

03 / POLICY

Разрешение на каждый вызов

Фильтрация каталога должна дополняться проверкой исполнения. Политика учитывает параметры и целевой объект, а backend проверяет доступ к данным. S10S11

04 / ПОКРЫТИЕ

Название продукта мало говорит

Gateway может быть API-конвертером, tool proxy, identity broker или локальным runtime. Эти классы закрывают разные потребности; сравнение по названию вводит в заблуждение.

05 / РЫНОК

Версия и редакция имеют вес

Важны ограничения MCP primitives, версия data plane и состав Enterprise. Portkey уже относится к Palo Alto Networks; старые рейтинги быстро устаревают. S14S17S37

06 / ВНЕДРЕНИЕ

PoC должен проверять обход

Критические тесты — прямой tools/call, смена tenant/arguments, отзыв token, сбой policy engine и доступ мимо gateway. Ниже подготовлена готовая программа пилота.

Обзор основан на документации и публикациях компаний. Продукты не развёртывались и не проходили сравнительный нагрузочный или security-тест. Рекомендации и критерии PoC — авторский анализ.

LLM gateway и MCP gateway

LLM gateway управляет обращениями к моделям: routing, quotas, бюджеты, policies на prompts и ответы. MCP gateway управляет доступом к инструментам: discovery, вызов, аргументы, identity и upstream credentials. Вендор может объединять оба контура в одном продукте.

Сканирование исходного prompt не даёт полного контроля над tool action: модель может получить новые инструкции из документа или результата предыдущего tool. Поэтому policy решения нужны на границе исполнения.

Проверять семантику MCP

Обычный HTTP proxy видит путь вроде /mcp. Protocol-aware gateway различает tools/list, tools/call, имя tool и параметры внутри сообщения. Контроль на уровне URL не обеспечивает эту гранулярность автоматически.

Отдельно фиксировать поддержку stdio, Streamable HTTP, legacy SSE, resources, prompts и extensions. Текущая спецификация различает транспорт и семантику протокола. S03S22

Identity forwarding ≠ произвольный token passthrough. Каждый принимающий сервис должен проверять, что token предназначен ему. На следующей границе используют подходящий scoped credential или token exchange. Передача одного bearer token во все backend APIs нарушает границы audience. S01S02S25

02 / Практика компаний

Что действительно опубликовано

Четыре именованных примера показывают разные этапы зрелости: собственный gateway, применение готового стека, identity middleware и управляемый набор локальных MCP.

Uber

01 октября 2026
Внутренний gateway · production по сообщению компании
800+ / 5 000+
MCP-серверов / tools

Собственный gateway объединяет registry/control plane и runtime/data plane. Он публикует существующие HTTP, gRPC и TChannel сервисы как tools и подключает native MCP. Команды сервисов сохраняют ownership: новые tools выключены до review, изменения описаний требуют согласования и допускают rollback.

Авторизация по humans/services/agents, tool-level overrides и redaction чувствительных ответов. Для внешних сервисов отдельный компонент обменивает внутреннюю identity на third-party credential.

Вывод для архитектуры. Заимствовать модель ownership и controlled enablement; число подключённых tools само по себе не показывает уровень безопасности.
S04

Cloudflare

14 апреля 2026
Внутренняя практика · поставщик применяет свой стек
SSO + DLP
контроль доступа и потоков данных

Компания описывает централизованное размещение remote MCP для внутренних источников. Сотрудники подключаются через Access и MCP server portals; администраторы управляют набором доступных tools и DLP.

Отдельный сетевой контроль обнаруживает remote MCP, к которым обращаются в обход portal: по доменам, путям и JSON-RPC признакам. Это расширяет покрытие за пределы одного endpoint.

Вывод для архитектуры. Маршрутизация через gateway становится границей защиты только при контроле обходных путей. Self-report поставщика не является независимым тестом.

Bloomberg

06 января 2026 · японская публикация
Внутренняя архитектура · identity middleware
User + workload
две identity в цепочке доступа

Bloomberg описывает remote multi-tenant MCP-инфраструктуру с middleware для identity, access control и observability. Клиентский proxy выполняет SSO/authentication; identity exchange формирует канонические identity пользователя и workload.

Компания также описывает развитие внутреннего registry с metadata и usage policies. Это показывает переход от интеграции отдельных tools к общему governance.

Вывод для архитектуры. Делегация identity — самостоятельная инфраструктурная задача. Внешний Bloomberg Enterprise MCP, анонсированный в сентябре, — отдельный продукт с entitlements и audit.

Block

22 апреля 2025
Историческая практика MCP · наличие gateway не подтверждено
Curated tools
одобренные собственные интеграции

Команда goose сообщает о повседневном использовании MCP тысячами сотрудников. В описанной конфигурации внутренние MCP написаны инженерами Block, одобренный набор предустановлен, OAuth встроен в локальные серверы, tokens хранятся в keychain.

Корпоративные model endpoints, ограничения на категории данных и в отдельных серверах — LLM allowlists и ограничения передачи результатов между системами.

Вывод для архитектуры. Полезный пример governance до централизации. Публикация не доказывает внедрение MCP gateway или текущее состояние Block в ноябре 2026.

Общий архитектурный паттерн — аналитический вывод. Повторяются curated tools, сохранение корпоративной identity, единые policies и наблюдаемость. Для утверждения «компания использует продукт X в production» нужна прямая публикация именно об MCP gateway. Общие customer logos и кейсы LLM gateway в этом отчёте таким доказательством не считаются.

Три уровня доступа

Сервер: можно ли подключаться к HR MCP.
Tool: можно ли вызывать get_salary.
Объект / транзакция: чью зарплату можно читать и с какой целью.

Gateway удобен для общих первых двух уровней и части условий третьего. Проверка владельца записи и row-level security обычно остаётся у системы данных.

Три потребителя платформы

Разработчику нужен удобный approved path: один endpoint, каталог и понятная ошибка.
Security/IAM — identity, policies, revoke, approvals и audit.
SRE — HA, latency, throughput, version compatibility и предсказуемый отказ.

Решение должно работать для интерактивных пользователей и автономных workloads с разными способами authentication.

04 / Риски и границы защиты

Что шлюз может ограничить —
и где нужен другой контроль

Gateway способен сократить доступный агенту набор действий и данных даже при ошибке модели. Полнота защиты зависит от прав в backend и охвата всех путей исполнения.

Модель угроз — синтез автора по MCP security best practices, OWASP guidance и описаниям lifecycle/security controls. S01S19S27S45

Сценарий: прочитать внутренний документ → отправить его наружу. Пользователь может иметь право и на поиск документов, и на отправку сообщения. Две отдельные проверки «tool разрешён» пропустят такую цепочку. Для ограничения нужны data classification, destination policy, контекст workflow и согласование high-impact действий. DLP помогает, но не заменяет модель прав на данные.

Gateway — критичный security asset

Здесь сходятся credentials, policy и маршруты к внутренним системам. Компрометация control plane расширяет blast radius. Нужны минимальные admin-права, сегментация, patching и контроль регистрации новых upstream адресов.

Публичный IBM bulletin об SSRF в OAuth registration ContextForge — конкретный пример такого класса риска; документ указывает исправление в 1.0.6. Наличие advisory не используется как сравнительный рейтинг продукта. S27

Доверять контексту только по происхождению

Заявленные агентом «task», «approved=true», «model=trusted» или tenant header не должны автоматически становиться основанием доступа. Эти атрибуты нужно получать из доверенной identity или проверенного workflow.

Внешний gateway обычно не знает, какая модель фактически инициировала действие: для model-specific policy нужен доверенный orchestrator или связанная телеметрия.

от существующей инфраструктуры

Ниже — рекомендации автора для пилота. Они основаны на публично описанном соответствии сценариям; прямых сравнительных испытаний продуктов не проводилось.

Основная среда — AWS

Начать с AgentCore Gateway

Удобный baseline для API/Lambda и cloud IAM. Проверить Policy scope, private connectivity, outbound OAuth и все используемые MCP primitives.

Уже внедрены Azure APIM / Entra

Начать с Azure API Management

Снижает объём новой платформенной интеграции. Если нужны resources/prompts или сложная per-tool policy, сначала подтвердить архитектурное покрытие.

Корпоративный Zero Trust на Cloudflare

Проверить MCP server portals

Сильное соответствие доступу сотрудников и сетевому governance. Проверить DLP entitlement, supported transport, service identity и прямой обход.

Сильная команда API platform

Kong / Gravitee / Traefik Hub

Выбирать вокруг текущего API stack и нужной гранулярности policy. У Traefik интересен transaction context; у Kong — явные per-tool ACL и CEL.

Нужен контроль над кодом и размещением

agentgateway / ContextForge / ToolHive

agentgateway — proxy/policy; ContextForge — registry/federation/plugins; ToolHive — runtime/registry/vMCP. Сравнить поддержку, state management и стоимость эксплуатации.

Хотите один governance для LLM и tools

Prisma AIRS / Bifrost / TrueFoundry

Проверить, связаны ли user/agent identities между model и tool traffic. Общий интерфейс сам по себе не гарантирует общего policy enforcement.

Главная боль — delegation и credentials

Aembit + текущая MCP-платформа

Пилотировать blended identity, token exchange, per-user isolation и отзыв доступа. Убедиться, что модель client identity соответствует вашей угрозе.

Нужен быстрый rollout или inspection

MintMCP / Lasso; Docker для local runtime

MintMCP — managed onboarding; Lasso — content inspection и scanner; Docker — управление локальными контейнерами. Сценарии различаются, одного PoC на все три недостаточно.

Build vs buy

Строить самостоятельно имеет смысл при нестандартной identity, собственном service mesh и готовой platform-команде — как в опубликованной архитектуре Uber. Для большинства организаций разумно сначала пилотировать готовый data plane, а внутренние усилия направить на policies, backend ACL, onboarding и контроль обхода. Самостоятельный proxy становится полноценной платформой только вместе с эксплуатацией, incident response и совместимостью клиентов.

Порядок принятия решения. Сначала исключить варианты, которые не проходят обязательные identity, data residency, protocol и deployment требования. Затем сравнить кандидатов на одном PoC corpus и реальной нагрузке. Баллы не должны компенсировать провал критической границы доступа.

07 / Внедрение и PoC

Проверить защиту
до расширения автономности

Предлагаемый план на 90 дней рассчитан на ограниченный пилот с последующим масштабированием. Сроки — рабочий ориентир автора, зависящий от зрелости IAM и интеграций.

ДНИ 01—30

Инвентарь и базовый маршрут

Определить AI-клиенты, MCP, владельцев и чувствительность данных. Выбрать 2–3 сценария преимущественно read-only. Включить SSO, минимальные credentials, audit и approved registry; измерить текущую нагрузку.

Результат: известны активы и границы, выбранные tools доступны только согласованным пользователям.

ДНИ 31—60

Доказать enforcement

Выполнить тесты identity/tenant isolation, direct invocation и обхода. Настроить DLP и schema review. Подключить SOC/SIEM, определить fail modes и протестировать отзыв доступа.

Результат: пройдены критические security gates, есть evidence и ответственные за эксплуатацию.

ДНИ 61—90

Ограниченные write workflows

Добавить несколько операций записи с transaction policy, approvals и idempotency. Провести нагрузочный тест полного security path, recovery exercise и staged rollout по командам.

Результат: согласованы SLO, стоимость, поддержка, rollback и условия дальнейшего расширения.

Общая стоимость складывается из лицензии и usage, инфраструктуры, identity/inspection, логирования, onboarding коннекторов и эксплуатации. Каталог из сотен tools требует постоянного владения политиками.

Иллюстрация · не коммерческое предложение

AWS: Gateway + Policy

≈ $30 / 1 млн calls

В опубликованных AWS примерах InvokeTool оценивается в $5 за миллион, Policy — $0,000025 за authorization request. При одном policy evaluation на один call получается $5 + $25.

1 000 000 × $0.000005
+ 1 000 000 × $0.000025
= $30

Только две составляющие. Не включены поиск, listing/health checks, logs, сеть, Lambda, guardrails, compute и прочие сервисы. Применимость тарифа и регион проверить перед закупкой. S13

Публичная ценовая единица

Aembit: лицензирование agents

$20 / agent / мес.

Teams начинается от 10 agents; арифметический старт — $200/мес. Starter включает 3 agents и ограниченные policies/retention. Enterprise — индивидуальные условия.

«Agent» в прайсе может обозначать приложение/клиент, а не человека, workflow или отдельный вызов. До сравнения TCO закрепить точное определение единицы и нужный срок хранения audit. S35

Примеры отражают разные модели оплаты и не предназначены для сравнения стоимости AWS и Aembit между собой.

Что включить в запрос цены. Users и workloads; число серверов/tools; requests, concurrency и payload sizes; регионы; HA/DR; private data plane; длительность audit retention; SSO/SCIM; support/SLA; inspection API и экспорт в SIEM. Уточнить, какие Enterprise-функции отсутствуют в OSS и бесплатном tier.

Коммерческие цены большинства enterprise-конфигураций публично не подтверждены. Наличие self-hosted data plane не означает, что payload, metadata, telemetry или secrets никогда не обращаются к внешнему control plane. Это проверяется по архитектуре, настройкам и условиям поставки. Доступность продукта, договорные условия и нужные регионы проверяются отдельно для конкретной организации.
